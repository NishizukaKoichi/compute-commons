# Compute Commons v1.0 目標仕様書

**状態:** 目標仕様確定／実装および第三者セキュリティ監査は未完了  
**プロトコル名:** `compute-commons/1`  
**ライセンス方針:** MIT互換のオープンソース  
**位置づけ:** Arcane Commons Meshが暗号化された永続保存層、Compute Commonsが分散実行層を担う。

## 0. 定義

Compute Commonsとは、参加許可型、自己ホスト可能、共同体所有の分散計算網である。参加者は、自分のパソコンに余っているCPU、GPU、メモリ、一時ストレージを任意に提供する。他の参加者は、承認済みワークロード、明示されたプライバシー条件、固定された資源上限、検証可能な実行記録、非金融的な内部クレジット台帳を通してのみ、その計算資源を利用できる。

目的は、希少性を人工的に作ることでも、トークンを発行することでも、無意味な計算を報酬化することでもない。文書分類、音声認識、画像処理、埋め込み生成、承認済みローカルモデル推論、再現可能な研究計算など、共同体が実際に必要とする仕事を実行するための仕組みである。

このシステムは、同時に四つの主権を守らなければならない。

1. 依頼者は、入力、出力、復号鍵の所有権を持つ。
2. ノード提供者は、自分の機械をいつ、どの範囲で使わせるかを決める。
3. 共同体は共通規則を決めるが、資金力、保有機材、クレジット量を政治権力へ変換させない。
4. 調整サーバー、管理者、保守担当者、創設者が消えても、別の運営者へ移行して復旧できる。

## 1. 絶対に破ってはならない原則

Compute Commonsは、次の条件を必ず守る。

- 依頼者が選んだものより弱いプライバシー階層へ、黙って降格してはならない。
- 保存時暗号化と通信暗号化を、計算中の内容保護であるかのように説明してはならない。
- ファイルを断片化したという理由だけで、機密平文を通常ノードへ渡してはならない。
- 検証を通過した有用な計算だけが、貢献クレジットを生む。待機時間や自己申告だけではクレジットを得られない。
- クレジットは、送金、売買、換金、交換、利息、ステーキング、貸借、担保化、投票権化を禁止する。
- 一人の人間は一票とする。ノード数、機材価格、クレジット残高、寄付額によって票を増やせない。
- 共同体の審査を受けていない任意のネイティブコードを、参加者の機械で実行してはならない。
- 調整サーバー、保存ノード、計算ノードの運営者へ、依頼者の復号鍵を渡してはならない。
- セキュリティ上重要な操作は、すべて署名済み監査イベントを残す。
- 中央的な役割を持つ各構成要素には、データ出力、移行、交換の手順を用意する。
- 破壊的な操作には、待機期間、複数人確認、異議申立て、復旧手段を設ける。
- 画面上では、「守られているもの」「露出量が減るだけのもの」「守られないもの」を明確に区別する。

## 2. 技術的な現実とプライバシー境界

データには、保存中、通信中、計算中という三つの状態がある。Arcane Commons Meshは保存中のデータを守り、暗号化されたQUIC通信は通信中のデータを守る。しかし一般的な計算では、処理可能な平文またはそれに相当する表現を、どこかのメモリ上へ展開しなければならない。

WebAssemblyのサンドボックスは、許可された能力だけをワークロードへ与えることで、依頼者側のコードからノード提供者のパソコンを守る。しかし、それだけでは、ホストOSを支配するノード提供者からワークロード内の秘密を守れない。

音声、文書、画像を分割すれば、一台へ渡る量は減る。だが、一つの断片だけでも内容を理解できる場合がある。したがって分割は、漏えい時の被害範囲を小さくする手段であって、機密性そのものではない。

機密ジョブには、次のいずれかを要求する。

- 遠隔認証されたTrusted Execution Environment。依頼者がハードウェア状態、実行環境、ワークロード測定値を確認した後にだけ鍵を渡す。
- FHEやMPCなど、対応している限定的な演算を、通常の平文鍵を渡さずに実行する暗号計算方式。

Compute Commonsは明示的なプライバシー階層を持ち、対応できない組み合わせは拒否する。弱い方式への自動切替は行わない。

## 3. 対象範囲

### 3.1 v1で対象とするジョブ

v1では、分割可能、再試行可能、一定時間内に終了するバッチ処理を主対象とする。

- 文書の分類、タグ付け、情報抽出、形式変換
- 独立して処理し、後で結合できる区間単位の音声認識
- 画像のリサイズ、タイル分割、特徴抽出、承認済み分類
- 一定量ごとの埋め込み生成
- 一つのタスクを一台の適格ノードで実行する、承認済みローカルモデル推論
- 決定論的な前処理と後処理
- 承認済みの科学計算、研究計算、共同体向け計算
- 集約処理を依頼者端末または適格な機密ノードで行えるMap／MapReduce処理

### 3.2 v1では対象外とするもの

- 完全匿名かつ無許可で参加できる公開ネットワーク
- Proof of Work、採掘、暗号資産、ウォレット、市場入札
- 依頼者が自由に渡したシェルスクリプトや任意OCIイメージの実行
- 不安定な家庭回線をまたいだ、LLMのレイヤー単位リアルタイム分散推論
- TEEを持たない通常ノード上での機密計算
- FHEによる完全汎用AI推論
- 大規模モデルのノード横断分散学習
- 実行検証が通ったという理由だけで、AI出力の事実性まで保証すること
- あらゆる物理攻撃、全サイドチャネル、ハードウェア供給網侵害への完全耐性

## 4. 役割と権限分離

**Member**は、共同体へ参加を認められた人間である。一人で複数ノードを所有できるが、統治上の本人識別は一つだけ持つ。

**Requester**はジョブを作成し、入力、出力、復旧情報を所有する。

**Node Operator**は機械を提供し、利用時間、CPU、GPU、温度、電池、メモリ、通信量などの上限を決める。

**Workload Maintainer**は、変更不能なワークロード版とマニフェストを公開する。

**Coordinator Operator**は、スケジューリングとメタデータサービスを運用する。ただし、ジョブの平文や復号鍵を取得しない。

**Verifier**は、結果、重複実行、カナリア、実行記録、ポリシー適合性を検査する。

**Key Guardian**は、依頼者不在時の機密鍵解放へ参加する。可能な限り調整サーバー運営者とは分離する。

**Security Steward**は、時限的な緊急手続きにより、問題のあるワークロード、ノード、リリースを隔離できる。

**Auditor**は、署名済みメタデータ、ソフトウェア来歴、統治操作、台帳整合性を確認できる。ただし平文ジョブへはアクセスできない。

いずれの役割も永久ではない。権限には、対象範囲、有効期限、失効手順を持たせる。

## 5. システム構成

### 5.1 Requester Client

Tauri製デスクトップアプリとCLI。依頼者端末内で、前処理、プライバシー分類、暗号化、ジョブ作成、費用見積り、結果復号、復旧、最終確認を行う。

### 5.2 Worker Agent

ノード提供者が導入するRust製デーモン。大まかな能力情報を提示し、署名済みリースを受け取り、承認済みワークロードだけを実行し、ローカル資源制限を強制し、実行記録を作成する。提供者は即座に一時停止できる。

### 5.3 Execution Runtime

Worker Agentは、次の四種類の実行方式を扱う。

- `wasm-component`: 移植性と能力制限を重視した、標準CPU実行方式
- `approved-model-adapter`: 公開モデルや非機密GPUジョブ向けの固定アダプター。依頼者による任意GPUカーネルは許可しない
- `confidential-oci`: 対応ハードウェア上の、遠隔認証された機密VMまたは機密コンテナ内で動く署名済みワークロード
- `cryptographic-plan`: 将来導入する、承認済みFHE／MPC演算グラフ

### 5.4 Coordinator

交換可能な制御面。会員参照、ノード稼働状況、能力照合、待ち行列、リース、配置用の粗いメタデータ、ジョブ状態、検証状態、クレジット予約を扱う。平文入力、平文出力、Recovery Kit、依頼者の復号鍵は保存しない。

### 5.5 Workload Registry

変更不能なワークロードパッケージ、スキーマ、モデル参照、SBOM、ビルド来歴、署名、資源プロファイル、最低プライバシー階層、検証規則を内容アドレス方式で管理する。

### 5.6 Attestation Verifier

ハードウェア証拠、Trusted Computing Baseの版、実行環境の測定値、ワークロードのダイジェスト、一時鍵との結合を、共同体が署名したポリシーと照合する。

### 5.7 Key Release Service

依頼者不在時の機密ジョブでは、タスク鍵を五つに分割する。三者以上の独立したGuardianが、適切な遠隔認証を確認した場合に限り、認証済み環境の一時鍵へ暗号化して各鍵片を解放する。依頼者がオンラインの場合は、依頼者端末が直接認証し、直接鍵を渡す方式を優先する。

### 5.8 Result Verifier

完全一致、許容誤差、定足数、カナリア、遠隔認証、スキーマ検査、意味検査、依頼者確認を組み合わせて結果を判定する。

### 5.9 Credit Ledger

貢献、利用、失効、基本付与、取消し、管理訂正を追記専用で記録する。送金操作は存在しない。

### 5.10 Arcane Commons Mesh

暗号化された入力、出力、チェックポイント、ワークロードパッケージ、署名済みスナップショット、監査ルートを保存する。Compute CommonsはCIDで参照し、一つの調整サーバーのローカルディスクを唯一の保存先にしない。

## 6. プライバシー階層

各ジョブは、必ず次のいずれかを指定する。スケジューラーは、これを変更不能な適格条件として扱う。

### P0 — Public

入力とモデルを、ノード提供者が閲覧できる可能性がある。保存と通信は暗号化するが、計算内容についてはホストを信頼する。公開データ、公開モデル、合成データ向け。

### P1 — Minimized Shard

依頼者端末で可能な限り直接識別子を除去し、仕事を小さな断片へ分ける。ただし、ノード提供者は断片を閲覧できる可能性がある。単独断片の漏えいを許容できる場合だけ使用する。画面には「ノード提供者がこの断片を読める可能性があります」と常時表示する。

### P2 — Attested CPU

承認済みCPU TEE内で実行する。認証された実行環境、ワークロードダイジェスト、ポリシーが確認された後だけ、タスク鍵を解放する。平文は設計上、認証済み環境内へ限定する。

### P3 — Attested Accelerator

承認済みCPU機密環境と、遠隔認証可能な機密アクセラレーターの両方を要求する。CPUとGPUの証拠が通過するまで鍵を渡さない。通常GPUへの切替は禁止する。

### P4 — Cryptographic

承認済みFHEまたはMPC計画を使う。計画が対応している演算だけを許可する。未対応のモデル層や演算があれば拒否し、平文方式へ切り替えない。

### Local-only

依頼者は `LOCAL_ONLY` を指定できる。このジョブは共同計算網へ出さず、依頼者が管理する端末だけで実行する。

入力の機密性、モデルの機密性、出力の機密性は別々に記録する。公開モデルと機密入力の組み合わせと、機密モデルと公開入力の組み合わせは、異なるポリシーとして扱う。

## 7. ワークロードパッケージ仕様

ワークロードの各版は変更不能とし、ダイジェストで識別する。内容を変更した場合は新しい版と新しいダイジェストを作り、再承認を受ける。

各パッケージは、次を含む。

- 名称、セマンティックバージョン、変更不能なダイジェスト
- 実行方式とエントリーポイント
- 入力スキーマと出力スキーマ
- 要求するホスト能力
- 原則通信禁止のネットワークポリシーと、例外がある場合の許可先
- CPU、RAM、VRAM、一時ディスク、出力量、実行時間の上限
- 対応OSとCPUアーキテクチャ
- 最低プライバシー階層
- 決定論的または確率的であることの宣言
- 乱数シード規則と数値許容誤差
- 分割方式と結合方式
- チェックポイント形式と互換版
- 結果検証方式
- 計量プロファイルと基準費用表
- モデルダイジェスト、ライセンス、キャッシュ方針
- SBOM、ソース参照、ビルド来歴、保守者署名
- 保持期間とログ方針
- 既知の制約と禁止データ分類

可変タグをセキュリティ上の識別子として使わない。スケジューリングでは変更不能なダイジェストだけを使用する。

新規ワークロードは、自動検査と人間による承認を必要とする。高リスクのワークロード分類は、最低二人の独立した保守者が承認する。緊急隔離は即時に新規リースを停止できるが、統治手続きで追認されなければ失効する。

## 8. ホスト能力モデル

標準状態では、ワークロードへ何の能力も与えない。承認済みマニフェストに明示された能力だけを渡す。

次は原則禁止する。

- 任意のホストファイルアクセス
- ホームディレクトリ、ブラウザ情報、SSH鍵、アプリ秘密情報
- クリップボード、カメラ、マイク、画面取得
- ローカルネットワーク探索
- 任意の外部通信
- プロセス列挙、ホストシェル実行
- 永続的なレジストリ変更や自動起動登録
- 他タスクへの直接アクセス
- 決定論が必要なジョブにおける無制限の時刻、乱数、機材識別子

許可するホスト呼出しは、割り当てられた暗号化Blobの読込み、出力Blobの書込み、進捗報告、チェックポイント保存、キャンセル状態確認など、狭く定義されたものに限定する。

モデルと依存物の取得は、タスク実行環境の外で行う。すべての取得物は、ダイジェストと署名を確認した後にだけ実行環境へ渡す。

## 9. ジョブマニフェスト

ジョブは、署名され変更不能な依頼内容と、変化する実行状態から成る。署名対象は決定論的に符号化する。

最低限、次の項目を持つ。

```yaml
spec_version: compute-commons/job/v1
job_id: 01J...
owner_key_id: ed25519:...
created_at: 2026-08-02T08:00:00Z
expires_at: 2026-08-03T08:00:00Z

workload:
  digest: blake3:...
  version: 1.2.0

privacy:
  tier: P2_ATTESTED_CPU
  input_confidential: true
  model_confidential: false
  output_confidential: true
  metadata_size_bucket: 64MiB

input:
  encrypted_manifest_cid: blake3:...
  key_release: OWNER_OR_3_OF_5_GUARDIANS

resources:
  cpu_threads_max: 4
  memory_mib_max: 8192
  gpu_required: false
  scratch_mib_max: 4096
  wall_time_seconds_max: 1800
  network_policy: DENY_ALL

split:
  strategy: MAP
  target_task_seconds: 300
  overlap_policy: workload-defined

verification:
  mode: ATTESTATION_PLUS_SPOTCHECK
  sample_replication_percent: 5
  numeric_tolerance: null

checkpoint:
  enabled: true
  interval_seconds: 300

credits:
  max_reserved_ccu: 900

output:
  recipient_key_id: x25519:...
  retention_policy: OWNER_MANAGED
```

依頼者が明示的に公開しない限り、調整サーバーへ元ファイル名、フォルダ階層、平文プロンプト、自由記述の内容説明を渡さない。

## 10. 暗号設計

Compute Commonsは、署名鍵と鍵合意用鍵を分離しつつ、Arcane Commons系の暗号方針を再利用する。

- Ed25519で、本人識別、マニフェスト、実行記録、統治操作、台帳イベントへ署名する。
- X25519を利用したHPKEで、タスク鍵を依頼者、Guardian、認証済み一時受信鍵へ包む。
- XChaCha20-Poly1305で、入力、出力、チェックポイントを暗号化する。
- HKDFで、依頼者が管理するルートからジョブ鍵とタスク鍵を分離生成する。
- BLAKE3で、平文コミットメント、暗号化オブジェクト、内部マニフェストを識別する。
- Argon2idで、人間のパスフレーズからRecovery Kit保護鍵を導出する。

各タスクは固有鍵を持つ。一つのタスク鍵が漏れても、兄弟タスクやジョブルートを復号できない構造とする。

機密タスクでは、認証済み環境内で一時X25519鍵を生成する。その公開鍵とワークロード測定値を遠隔認証証拠へ結びつける。依頼者またはGuardianは、その結びつきが確認できた鍵に対してだけ、タスク鍵情報を渡す。

秘密情報を、コマンド引数、環境変数、通常ログ、調整サーバーのデータベース項目へ置かない。

監査済みライブラリを利用し、新しい暗号プリミティブを独自発明しない。

## 11. ジョブ実行の流れ

1. 依頼者が承認済みワークロードとプライバシー階層を選ぶ。
2. 依頼者端末内で、必要な匿名化、正規化、分割計画を行う。
3. 提出前に、最大CCU見積りを算出する。
4. ジョブルート鍵と、互いに独立したタスク鍵を生成する。
5. 入力をローカルで暗号化し、Arcane Commons Meshへ保存する。
6. 署名済みジョブマニフェストと、機密性の低い配置用メタデータだけを提出する。
7. CoordinatorがCCUを予約し、タスク記録を作成する。
8. 適格ノードへ短時間有効なリースを提示する。
9. P2またはP3では、鍵解放前に遠隔認証を通す。
10. ノードが暗号文を取得し、ポリシーに従ってタスク鍵を受け取り、指定実行環境で処理する。
11. 実行環境が結果を依頼者鍵へ暗号化し、チェックポイントまたは最終出力を保存する。
12. ノードが署名済み実行記録と出力コミットメントを提出する。
13. Verifierが指定された規則で検証する。
14. 承認結果を依頼者へ提示し、提供者の貢献CCUと依頼者の利用CCUを確定する。
15. 不正、欠落、失敗タスクは、二重課金せず再投入する。
16. 適合実装は、一時鍵、平文メモリ、一時領域を終了時に破棄する。
17. 最終結合は依頼者端末で行う。ただし、承認済み機密Reducerを指定した場合はその限りではない。

ジョブ状態は、`DRAFT`、`QUEUED`、`RESERVED`、`RUNNING`、`VERIFYING`、`COMPLETED`、`FAILED`、`CANCELLED`、`EXPIRED` とする。

タスク状態は、`PENDING`、`OFFERED`、`LEASED`、`RUNNING`、`CHECKPOINTED`、`SUBMITTED`、`ACCEPTED`、`REJECTED`、`REQUEUED` とする。

## 12. 分割と結合

スケジューリングの基本単位は、プロジェクト全体ではなく、再実行可能なタスクとする。

対応方式は次の通り。

- `MAP`: 各入力断片を独立処理する。
- `MAP_REDUCE`: 各ノードが暗号化された中間結果を作り、依頼者または機密Reducerが結合する。
- `PIPELINE`: 承認済み各段階が、型付き暗号化出力を次段階へ渡す。
- `REPLICATED`: 同一または比較可能な仕事を複数障害領域へ送り、結果を検証する。
- `SINGLE_NODE`: 一つの完全な推論要求を、一台の適格ノードで実行する。

具体例は次の通り。

- 音声は、ワークロードが定めた重複区間を持つ時間窓へ分割し、依頼者側で時刻と重複を統合する。
- 文書は、一文書または一ページの漏えいを許容できる場合に限り、その単位で分割する。
- 画像は画像単位またはタイル単位で分けられるが、タイル化を機密性として説明しない。
- 埋め込みは一定件数ごとに処理する。
- LLMプロンプトは、v1では一つの完全な要求として一台へ送る。共同体ノード間でのトークン単位モデル分割は行わない。

分割方式は、複数断片を組み合わせることで新たな情報が露出するかを宣言する。P1の関連断片は可能な限り異なる障害領域へ配置するが、複数ノードの共謀可能性は残るものとして扱う。

## 13. ノード提供者の操作権

ノード提供は任意であり、機械の最終権限は提供者にある。Worker Agentは次を用意する。

- 利用可能な曜日と時間帯
- CPUスレッド数とCPU使用率上限
- RAMと一時ディスク上限
- 明示的なGPU有効化とVRAM上限
- 電源接続中のみ動かす設定
- 利用者操作を検出した際の一時停止
- 温度上限と自動冷却待機
- 通信量上限とRelay利用方針
- 許可するプライバシー階層とワークロード分類
- 即時停止、一時停止、Drain
- ノード削除と証明書失効
- 実行履歴、資源利用、実行記録、獲得CCUのローカル表示

標準設定では、GPUを無効、電源接続必須、論理CPUの半分以下、RAM上限あり、ホストネットワーク禁止、利用者操作時停止、設定温度到達時停止とする。

ノードはいつでも離脱できる。通常の中断は統治上の違反としない。ただし、虚偽能力申告、実行記録偽造、故意の不正結果はセキュリティ事案として扱う。

## 14. スケジューリングとリース

スケジューラーは、最初に必須条件を適用し、その後で適格ノードを順位付けする。

必須条件には、プライバシー階層、実行方式、CPUアーキテクチャ、RAM、アクセラレーター種類、遠隔認証ポリシー、法域条件、依頼者制約、パッケージ対応状況を含む。

順位付けには、予想完了時間、運用信頼性、現在負荷、通信費用、温度余裕、障害領域の分散、チェックポイント位置、期限を使う。クレジットによる入札は禁止する。

検証用複製は、可能な場合、同一人物、同一世帯、同一調整サーバー、同一ネットワーク障害領域へ集中させない。

初期標準値は次の通り。

- リース提示の有効時間は30秒
- 実行中ノードは20秒ごとにHeartbeatを送信
- 三回連続でHeartbeatを失った場合は不安定状態
- 90秒以内に復旧しなければ再投入可能
- 一タスクの目標時間は2分から15分
- 15分を超えるタスクは、原則5分ごとにチェックポイントを作成
- 標準最大実行時間は30分。承認済み例外は2時間まで

実行保証はat-least-onceとする。結果確定処理は冪等とし、同じタスクIDの重複実行で、利用CCUまたは貢献CCUを二重計上しない。

優先度は `COMMUNITY_CRITICAL`、`INTERACTIVE`、`STANDARD`、`BATCH` とする。重みは統治で決め、支払いによって購入できない。共同体重要ジョブの発行量には上限を設け、監査ログへ残す。

## 15. 結果検証

Compute Commonsは、実行の完全性と、意味上の正しさを区別する。承認済みコードが指定入力に対して動いたことを示せても、モデル回答が現実世界で正しいとは限らない。

各ワークロードは、次の検証方式を一つ以上指定する。

### Exact

正規化済み出力バイトまたはハッシュが一致しなければならない。

### Tolerance

数値出力を、ワークロードが定めた許容誤差と正規順序で比較する。

### Quorum

複数ノードの結果を比較する。通常ノードで行う決定論的タスクは、原則二結果一致とし、不一致時に三つ目を送る。

### Canary

一部に、既知の性質または期待結果を持つ検査タスクを混ぜる。失敗が続いた場合、運用信頼度低下、ノード隔離、ワークロード隔離を行える。

### Attested

遠隔認証証拠、実行環境測定値、ワークロードダイジェスト、一時鍵、ポリシーが一致した場合に限り、実行記録を認める。

### Semantic Validator

別の承認済み検証器が、スキーマ、不変条件、信頼度範囲、領域固有条件を検査する。重大判断で必要な依頼者確認を、黙って置き換えてはならない。

### Owner Review

依頼者が明示的に承認または拒否する。モデル品質が主観的な場合、拒否を直ちにノード不正と判定せず、異議処理へ進める。

確率的AIワークロードは、乱数シード処理と決定論的カーネル要否を宣言する。ビット単位一致が妥当でない場合、遠隔認証、スキーマ検査、一部複製、領域固有検証を組み合わせる。

承認結果には、最低限、ワークロードダイジェスト、入力コミットメント、出力コミットメント、タスクID、リースID、開始終了時刻、資源分類、検証方式、必要な場合は遠隔認証ハッシュ、ノード署名を含む実行記録を作る。

## 16. 運用信頼度

運用信頼度は、スケジューリングとセキュリティにだけ使う。

- ノード単位かつワークロード分類単位
- 譲渡不可
- 原則非公開
- 投票権や他領域の特権へ変換不可
- 時間経過で中立値へ戻る
- 判定に異議申立て可能
- 人間としての社会的評価とは分離

全人間を一つの数値で評価する普遍的信用スコアを作らない。

## 17. Compute Commons Credits

内部単位を **CCU — Compute Commons Unit** とする。

一CCUは、版管理された `CC-REF` 基準実行環境上での、承認済み計算一秒分を表す。各ワークロード版は、入力サイズ区分と資源分類ごとの基準費用表を公開する。GPUおよび機密実行環境は、統治で承認された版付き換算表を用いる。

ノードは、実測経過時間ではなく、承認されたタスクの公開基準費用を受け取る。遅い機械が時間を引き延ばして多くのCCUを得ることはできない。速い機械は、単位時間により多くの有用タスクを完了することで、結果として多くのCCUを得る。

依頼者の最大消費量は実行前に予約する。

`reserved_ccu = primary_reference_cost + required_replica_cost + declared_verification_overhead`

最終消費量は、検証規則上必要となった承認済み計算量とし、依頼者の再承認なしに予約上限を超えない。

台帳イベントは次の通り。

- `BASIC_GRANT`
- `COMMUNITY_GRANT`
- `COMPUTE_CONTRIBUTED`
- `COMPUTE_CONSUMED`
- `EXPIRED`
- `REVERSAL`
- `ADMIN_CORRECTION`

`TRANSFER` は存在しない。依頼者から提供者へ直接支払うのではなく、共同体台帳が貢献と利用を別々に記録する。

初期標準値は次の通り。

- 活動中会員へ毎月3,600 CCUを基本付与
- 基本CCUは付与期間末に失効し、繰り越さない
- 貢献で得たCCUは90日で失効
- 古い利用可能CCUから先に消費
- 待機時間にはCCUを与えない
- 失敗、偽造、拒否結果にはCCUを与えない
- 再利用可能な承認済みチェックポイントは、マニフェストで定めた割合を付与可能
- 依頼者キャンセル前に完成した有効結果は貢献として認める
- 残高を負数にしない
- 残高不足では新規実行を止めるが、既存結果を削除しない

Arcane Commons Meshの保存クレジットと、Compute CommonsのCCUは別物とし、交換できない。

標準では公開ランキングを作らない。本人は自分の履歴を確認でき、共同体は総計算能力を確認できるが、永久的な序列を作らない。

## 18. 台帳と監査の完全性

台帳イベントと監査イベントは、すべて署名し、前イベントハッシュと結び、共同体内の単調増加番号を付ける。一定間隔でMerkle Rootと署名済みスナップショットを作り、Arcane Commons Meshへ複製する。

Coordinatorは高速参照用の状態を持てるが、権威を持つのは署名済みイベント列である。管理訂正は新イベントを追記し、過去を改変しない。

監査イベントには平文機密情報を入れず、コミットメント、ポリシーID、実行主体、理由コード、結果だけを記録する。

記録対象には次を含む。

- 会員と役割の変更
- ノード登録と失効
- ワークロード承認、隔離、隔離解除
- リース発行と終了
- 遠隔認証の承認と拒否
- 鍵片解放
- 結果の承認と拒否
- 基本付与、貢献、利用、失効、訂正
- Coordinator移行
- 緊急操作と失効
- 統治提案の実行

## 19. 統治

基本原則は、確認済み会員一人につき一票とする。

通常提案は、会員全体の20%を定足数とし、投票された賛否の単純過半数で可決する。

プライバシー保証の弱体化、CCUの非金融性、一人一票、復号バックドア禁止、管理者交換規則など、憲法的事項の変更には、40%の定足数と三分の二以上の賛成を要求する。

緊急セキュリティ操作には、現任Security Steward五人中三人の承認を要求する。リリース、ワークロード、ノード証明書分類、遠隔認証基準、Coordinator接続先を一時隔離できる。七日以内に追認されなければ自動失効する。

Registry履歴、台帳復旧情報、Key Guardian構成、共同体スナップショットへ影響する破壊的操作は、複数管理者、署名済み理由、最低24時間の待機、復旧可能な事前スナップショットを要求する。

機材提供量、資金提供量、CCU残高によって投票権を増やせない。

停止または隔離には、理由コード、証拠参照、期限または再審査日、異議申立て手順を持たせる。

## 20. 通信とプロトコル

通信プロトコル名を `compute-commons/1` とし、認証・暗号化されたQUIC上で動かす。端末間の直接接続を優先し、接続できない場合は共同体運営のRelayを利用する。

各メッセージは、次を含む署名済みEnvelopeを使う。

- プロトコル版
- メッセージ種別
- 送信者ID
- Request ID
- 発行時刻
- 失効時刻
- Body Digest
- 署名

通常要求の有効時間は最大五分とする。Request IDを十分な期間保存し、再送攻撃を拒否する。リースは独立したLease IDと状態遷移を持つ。

主要メッセージは次の通り。

- `HELLO`
- `CAPABILITY_ADVERTISE`
- `LEASE_OFFER`
- `LEASE_ACCEPT`
- `HEARTBEAT`
- `ATTESTATION_EVIDENCE`
- `KEY_GRANT`
- `BLOB_REQUEST`
- `CHECKPOINT_COMMIT`
- `RESULT_COMMIT`
- `VERIFICATION_RESULT`
- `TASK_CANCEL`
- `NODE_DRAIN`
- `AUDIT_CHALLENGE`

Relayは通信メタデータを観測できるが、アプリケーション平文は読めない。実運用では、交換可能な共同体専用Relayを持つ。

## 21. ソフトウェア供給網と更新

Worker Agent、ワークロードパッケージ、機密実行イメージ、モデルアダプターは、変更不能なダイジェストへ署名し、実行前に検証する。

ビルド処理は、来歴情報とSBOMを生成する。共同体ポリシーが、許可するビルダー、保守者、最低来歴水準を定める。

WorkerとCoordinatorの更新には、ルート鍵分離、期限、Rollback防止を持つ更新方式を用いる。配布リポジトリ一つが侵害されただけでは、署名されていない版を導入できない構造とする。

Workerは次を拒否する。

- 未署名パッケージ
- 固定されていない可変依存物
- 期限切れ更新メタデータ
- 承認マニフェストとダイジェストが異なるパッケージ
- 宣言外能力を要求するワークロード
- 測定済み実行環境がポリシーと異なる機密ジョブ

重大セキュリティ更新は自動提示できるが、ノード提供者へ内容を表示し、限られた延期期間を認める。失効版には新規ジョブを配らない。

## 22. メタデータ保護と保持期間

Coordinatorは、配置、会計、検証、復旧に必要な情報だけを保存する。

正確な入力サイズは一定幅の区分へ丸める。ファイル名、フォルダ階層、平文プロンプトは暗号化したままにする。正確な位置情報は要求せず、法域と大まかな障害領域だけを使う。

初期保持方針は次の通り。

- 適合する実行環境は、平文を通常Workerディスクへ意図的に書き込まない
- 暗号化タスクキャッシュは、終了またはリース失効後一時間で削除
- 機密一時領域は暗号化し、環境終了時に破棄
- チェックポイントは、依頼者が延長しない限りジョブ完了後24時間で削除
- Coordinatorの詳細タスクメタデータは90日保持
- 署名済み監査ルートと台帳ルートは恒久保持
- 詳細監査イベントは標準一年保持し、法的条件に応じ共同体が変更可能

悪意ある通常ホストは、受け取ったP0またはP1平文を複製できる。システムはこれを否定しない。削除記録は適合ソフトウェアの動作証明であって、平文閲覧を許された悪意あるホストに対する完全削除証明ではない。

## 23. 障害復旧

ノード離脱を前提に、タスクを設計する。リースを失った場合は、最後に承認されたチェックポイントから再投入する。結果確定は冪等とし、Task IDにより二重CCUを防ぐ。

依頼者のRecovery Kitは、本人識別鍵、暗号化済みジョブ鍵索引、未完了ジョブ参照、結果所有権を新端末へ復元する。元Coordinatorを必要としない。

Coordinatorは最低六時間ごとに署名済み状態スナップショットを出力する。新しいCoordinatorは、最新スナップショットを読み、署名済みイベントを再生し、未確定リースを無効化し、未完了タスクを安全に再投入する。

ワークロードパッケージ、基準ポリシー、監査ルート、Coordinator探索情報はArcane Commons Meshへ複製する。

依頼者不在時の鍵解放は三者以上／五者方式とする。Guardian交代には、署名済み移行記録と新旧併存期間を要求する。Coordinator単独ではタスク鍵を復元できない。

適格な機密ノードが消えた場合、機密ジョブは待機またはFail Closedする。弱い階層へは切り替えない。

## 24. 不正利用への耐性

初期ネットワークは参加許可型とする。招待、所属確認、共同体承認などによってSybil攻撃を抑える。

依頼者は、承認済みワークロードとスキーマに合うパラメータだけを提出できる。独自コードは審査を受けるか、`LOCAL_ONLY` で動かす。

ジョブ作成、認証失敗、リースの大量破棄、Blob取得、鍵解放要求にはRate Limitを設ける。

システムは、新規処理停止、証拠保存、証明書失効、異議申立てを行える。ただし、不正対策を理由に運営者用復号バックドアを作らない。

依頼者は、提出データを処理する権利を持ち、共同体規則と適用法へ従うことを表明する。必要に応じて、共同体ごとに対象ワークロードやデータ分類をさらに狭く制限できる。

## 25. 画面要件

依頼者画面は、提出前に次を表示する。

- 選択したプライバシー階層
- 誰が平文を見られる可能性があるか
- モデル重みがノードへ公開されるか
- CCU見積り幅と最大予約量
- 想定複製数
- 検証方式
- 保持方針
- 最終的な依頼者確認が必要か

P0とP1では、継続的な警告を表示する。保存暗号化が、通常ノードでの計算中平文を守るかのような表現は禁止する。

ノード提供者画面は次を表示する。

- 現在の資源使用量
- ワークロード分類とプライバシー階層。ただし機密内容は表示しない
- 温度、電池、通信状態
- 一時停止、Drain、停止
- 承認・拒否された実行記録
- 獲得CCUと失効日
- ソフトウェア版とポリシー版
- 機密ジョブ適格性

統治画面は、提案、緊急操作、役割有効期限、監査参照、Coordinator移行状態を表示する。

## 27. 開発段階

### v0.1 — Research MVP

CPUのみの `wasm-component` 実行。公開データまたは合成データだけを使う。署名済みパッケージ、タスク分割、リース、ノード中断、再投入、完全一致検証、重複防止、CCU計上、監査イベントを実証する。この段階ではホストに対する機密性を主張しない。

### v0.2 — 物理ネットワーク

二つ以上のネットワークに存在する三台以上の物理端末で、直接QUIC接続、Relay経由接続、Arcane Commons Mesh連携、暗号化チェックポイント、Coordinator復旧を実証する。

### v0.3 — Registryと統治

変更不能Workload Registry、ビルド来歴、安全な更新、一人一票、緊急隔離、異議申立て、Coordinator移行を実装する。

### v0.4 — 承認済みアクセラレーター実行

固定されたモデルアダプターを通して、非機密GPU推論を行う。任意GPUコードと、通常GPUへの機密入力は許可しない。

### v0.5 — Attested CPU

対応するCPU機密環境でP2ジョブを実行する。遠隔認証、依頼者直接鍵解放、三者以上／五者Guardian解放、認証失敗時に鍵が渡らないことを実証する。

### v1.0 — 監査済みBeta

第三者セキュリティ審査、明文化された脅威モデル、実運用復旧訓練、プライバシー表示審査、署名済みリリース手順、音声、文書、画像、モデル推論の各完成ワークロードを要求する。P3機密アクセラレーターは、対応ハードウェアだけの任意機能として残してよい。

### 将来仕様

P4暗号計算、汚染対策を備えたFederated Learning、複数共同体間連合、プライバシー保護スケジューリングは、別の審査済み仕様として追加する。

## 28. 受入試験

該当する試験を通過するまで、完成とはみなさない。

1. 未承認パッケージへリースを発行できない。
2. 署名後に一バイトでも変化したパッケージを拒否する。
3. Wasmワークロードが、許可されていないホストファイルを読めない。
4. 宣言されていない外部通信を開けない。
5. P2ジョブをP0／P1専用ノードへ配置しない。
6. 遠隔認証不一致時に鍵を渡さない。
7. Coordinatorデータベースを取得しても、入力と出力を復号できない。
8. ノード停止時に、チェックポイント復旧または安全な再投入が行われる。
9. 重複リースでCCUを二重発行できない。
10. 意図的に誤った決定論的結果を拒否する。
11. 一方が悪意ある複製でも、正しい検証複製には正当にCCUを付与する。
12. 同一承認タスクを遅く実行してもCCUが増えない。
13. 失効CCUを使えず、他者へ移せない。
14. ノード追加によって投票権が増えない。
15. 緊急隔離が、追認なしに自動失効する。
16. 失効ノード証明書では新規リースを受けられない。
17. ノード一時停止が、確定済み出力を破壊しない。
18. CPU、RAM、Disk、Battery、温度の上限を守る。
19. 適合する機密実行環境が、通常ログや永続一時領域へ平文を書かない。
20. 新端末でRecovery Kitから本人識別と暗号化結果へのアクセスを復元できる。
21. 新Coordinatorが、署名済みスナップショットとイベントから台帳とジョブ状態を再構築できる。
22. 過去の正しい署名要求を再送しても拒否する。
23. 提出前に、ノード提供者が平文を見られる可能性を依頼者が確認できる。
24. 創設者または元Coordinatorを取り除いても、共同体が計算、検証、復旧を継続できる。

## 29. 完成の定義

Compute Commonsは、次の文が理想ではなく技術的事実となったときに完成する。

> 参加者は、承認済みの有用な計算を依頼し、どのプライバシー保証が適用されるかを事前に知り、入力と出力の鍵を自分で所有し、通常のノード障害を越えて仕事を継続し、なぜ結果が承認されたかを検証できる。そして有用な貢献を記録しながら、それを貨幣や政治権力へ変えず、元の運営者が消えても別の運営者の下で仕組みを復旧できる。

Arcane Commons Meshは、機械を失った後にも共同体の記憶を守る。Compute Commonsは、個人データ、機械の主権、政治的平等を手放さずに、共同体の計算能力を共有できるようにする。
